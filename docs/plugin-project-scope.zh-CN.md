## 1. 问题

能不能让项目定制插件，同时保持插件生态可维护、可复现、安全？

## 2. 结论

**项目里的扩展就是插件，整包放进项目，像 Godot addons 那样随项目走；权限做减法；安全只做"打开项目不等于执行代码"这一件事。**

## 3. 原则（稳定层，修改需要很强的理由）

1. **一种格式、一个位置**：项目里的扩展（面板、Skills、工具、native）都是插件，统一放在 `.ohmygame/plugins/`。
2. **整包覆盖、不混用**：项目级插件覆盖同 id 的用户级插件，从不混用两边的文件。
3. **打开不等于执行**：打开一个项目不会运行它的代码，用户第一次主动操作之后才运行。
4. **安全投入与"概率 × 后果"相称**：不为极小概率的风险，让所有用户每天承担摩擦。权限只在安装用户级插件时问一次。
5. **复用优先**：能用现有机制（开发模式、checkpoint、Git、agent）解决的，不新建。

## 4. 推导要点

- **现有架构值得演进，不需要重写。** "声明式扩展点 + 权限"（#809）、场景驱动和扩展点纪律（#544、#672）、契约纪律（#598）、代码分层、供应链都很扎实。
- **实际需求集中。** 13 个预装插件里 9 个只有 Skills，只有 godot 和 taptap-maker 带 native。定制需求主要是 Skills、面板和少数整包修改。
- **整包复制最简单。** 这是从 Unity Customize 吸收的**原因**：共享的包不可变，才能缓存、校验、安全更新；项目里的副本可变，才能为项目修改。细粒度方案（只允许沙箱内容的项目副本、按视图转换、跨插件调用）都要发明新的身份规则和私有 API。
- **不做信任弹窗和沙箱。**
  - OhMyGame 的用户大多不是程序员，弹窗只会被点掉。
  - Claude Code 的沙箱能减少弹窗，是因为它的基线是"每条命令都问"；OhMyGame 的内置 agent 本来就不问，加盒子反而会新增询问。
  - 概率低、成本高，所以写下重新考虑的条件，暂时不做。
- **唯一要处理的实际场景是打开即执行。** 打开项目时 `project-shell.tsx` 以 `automatic=true` 调用 `acquirePreview`；默认设置下会先装依赖（包括 postinstall 脚本），再运行 `dev` 脚本。
- **项目面板单独成一套已经没有理由。** 它当初的三个约束（不能有 native、要单独审批、要用 `_project` 身份，#716）按本方案都不成立。

## 5. 范围（4 项）

| # | 内容 | 主要位置 | 规模（粗估） |
| --- | --- | --- | --- |
| 1 | **项目级插件**：放在 `.ohmygame/plugins/<publisher>/<name>/`，整包覆盖同 id 的用户级插件。项目有自己的索引，解析结果仍是普通 `PluginIndexEntry`，`root` 指向项目。监听和重载复用开发模式。<br>只新增一个动作"复制到项目"：再点一次就是覆盖更新；删掉文件夹就是还原；做成插件用现有的"从本机文件夹添加"。<br>agent 写的插件用保留的 publisher `project`。插件页和日志标出来源 | `resolveProjectPlugins()`、`plugin-development.ts`、`native-plugins.ts` 的校验路径、插件页 | 约 600–1,000 行（含测试） |
| 2 | **项目面板并入项目级插件**：<br>项目级插件的 manifest 校验放宽，做成插件或发布时再完整检查（`plugin-manifest.ts` 里"有面板的插件必须带图标"这类校验）；<br>插件页面也能用 `net.fetch`，主机沿用 `capabilities.network`（`plugin-ui-protocol.ts` 的 `PluginUiCapabilities.net`）；<br>页面报错写到 `.ohmygame/local/` 下给 agent 读；<br>`.ohmygame/panels/` 在加载时迁移一次（`panel-to-plugin.ts`）；<br>`workspace.ts` 改为对 agent 和 Code 面板显示 `.ohmygame/plugins/`，`project_guide` 改写 | 删除 `project-panels.ts`、`shared/project-panels.ts` 的独立流程，以及 `plugin-ui-server.ts` 的 `_project` 路径 | **净删除** |
| 3 | **权限减法**：<br>删除 `needs-approval` 状态和 `PluginGrants.projects`（迁移后移除）；<br>面板审批随第 2 项消失；<br>保留安装时同意、签名和下架标记、工具钩子和"允许并记住"、已有的显式流程、safe mode | `project-plugins.ts`、`PluginGrants` | **净删除** |
| 4 | **打开不等于执行**：<br>导入的项目和打开的外部文件夹，在用户第一次点 Play 或发消息之前不自动预览；<br>项目级插件在此之前也不加载。<br>（实现澄清：`previewAutoStart` 存在随项目走的 `.ohmygame/settings.json` 里，改它会在用户仓库产生 diff，所以改用**本机**项目记录里的 `origin` 和 `engagedAt` 来判断。意图不变，见实现计划第 3 节） | `projects.ts`、`project-archive.ts`、`preview.ts`、项目级插件的加载入口 | 约 50–100 行 |

### 验收标准

1. 把一个用户级插件复制到项目后，项目里用的是项目副本；删除副本后回到用户级版本；另一个项目不受影响。
2. agent 写的面板和 Skill 放在 `.ohmygame/plugins/project/<name>/` 下，保存后自动生效，不弹审批。
3. 旧项目的 `.ohmygame/panels/` 迁移后行为不变，包括 `net.fetch` 和报错日志。
4. 导入的项目打开后不安装依赖、不运行脚本、不加载项目级插件；点 Play 或发消息之后正常运行。
5. 项目级插件的钩子出错时，可以在项目的插件面板里关掉它，不依赖 agent 修复。

### 落地顺序

第 4 项 → 第 1 项 → 第 2、3 项。每步一个 PR，从 `dev` 拉分支、合回 `dev`，PR 里写明对应本文的哪一项。

## 7. 变更规则

1. 本文冻结。只有出现**新事实**（新数据、真实事故、实现中发现的冲突）才能提出修改。在 #1051 里以评论的形式写清理由，**维护者确认后才生效**。换个说法或"更优雅"不算理由。
2. 实现中发现计划行不通，就停下来回到 issue 提出，不在 PR 里自行调整范围或增加功能。
3. 每个 PR 写明实现的是第 5 节的哪一项，评审时检查范围是否和本文一致。
4. 本文放在仓库的 `docs/plugin-project-scope.zh-CN.md`，[`AGENTS.md`](../AGENTS.md) 里有一行指向它，让每次协作都从同一份计划出发。
