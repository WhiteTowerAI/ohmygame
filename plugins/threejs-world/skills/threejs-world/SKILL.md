# Three.js World

Turn the user's imagined place into a rich, coherent, editable Three.js world. High-detail, multi-scale visual finish and a themed presentation layer are the minimum delivery target. A runnable procedural scene or a functional HUD alone does not meet it.

Here, `agent` names the execution role, not a tool to discover or invoke. The agent chooses the Three.js implementation within the project constraints.

This skill covers scene and world building. When the user later wants rules, goals, scoring, or other game systems on top of the world, hand that work to `web-game-studio`.

### Asset batch production and soft checkpoints

For new worlds, organize production around dependencies rather than advancing one asset at a time. Complete the world design and major-region plan first, keep a complete but adjustable asset inventory, and resolve enough terrain, roads, and water-system structure to support the first placements. Then divide the inventory into dependency-aware batches. Submit mutually independent generation tasks in the same batch, let each task wait and download independently, and mark its state without blocking unrelated work. Only when a batch is ready for integration should the actual resource paths and Three.js scene entry be updated together; start or reuse one preview session for that batch and inspect the collected result as a group.

Do not make the default workflow “generate one model, edit the scene, restart the preview, and then continue.” Do not restart and close a preview for every model, and do not let one failed asset block independent assets. Meshy generation, real-path integration, runtime loading checks, and the full visual acceptance requirements remain mandatory.

Use these reversible checkpoints instead of freezing the whole design:

- **Design checkpoint:** regions, routes, major subjects, and visual goals are listed; the inventory may still change.
- **Spatial-foundation checkpoint:** terrain, roads, and water relationships support the first placements; local design changes remain allowed.
- **Asset-batch checkpoint:** the current batch is generated, downloaded, or explicitly marked `blocked`; later batches need not be finished.
- **Unified-integration checkpoint:** the current batch is written to the real resource paths and scene entry, then checked in one reused preview session.
- **Final-acceptance checkpoint:** local issues have been rechecked and the complete five-stage visual review is run once at the end.

## Design, build, inspect

1. **Understand the idea and scope.** Preserve the original request and later revisions in `.world/request.md`. Distinguish new worlds, local revisions, and discussion/plan-only tasks. Preserve explicit themes, places, functions, style, and exclusions; record reasonable inferences separately. An actual build request authorizes generation when OhMyGame exposes the tools and has usable credentials; do not ask for another written authorization. Honor prompt-only and no-generation boundaries. Follow the [provider rules](references/world-contract.md#3d-asset-provider-selection). If no Meshy, Hyper3D, or free Hyper3D access is currently usable and the user has not explicitly declined to provide both APIs, direct the user to OhMyGame's `Providers & Models` and wait for configuration; do not silently fall back to a procedural scene. Only an explicit user refusal to provide both APIs, together with no currently available free Hyper3D access, permits the documented all-procedural fallback. Never ask for or expose a key in chat or files.
2. **Expand the intent.** Read [the expansion guide](references/world-expansion.md), [the worked example](references/expansion-example.txt), and [the presentation guide](references/presentation.md). Start `.world/expanded-prompt.md` with regions, routes, landform relationships, core subjects, information density, building orientation relationships, and review views, without inventing precise coordinates before terrain planning. Establish the complete asset inventory and record dependencies, batch membership, integration paths, and status there. Buildings should respond to roads, rivers, terrain boundaries, and public spaces instead of forming an all-orthogonal grid. For new worlds, when Meshy, Hyper3D, or currently available free Hyper3D access can generate assets, plan at least 15 independent major generated subjects across at least three significant categories and all major regions; count qualifying Meshy and Hyper3D subjects together and complete the entire required set. Follow the [counting rules](references/world-contract.md#count-completed-generated-subjects).
3. **Plan terrain and refine the design.** For a new outdoor terrain world, follow [the terrain workflow](references/terrain-workflow.md) and the [agent handoff](references/terrain-agent-handoff.md): select and actually view 1–3 references, generate and view a top-down terrain semantic image with OhMyGame, then give the complete image, spatial brief, world coordinates, and Three.js constraints directly to the agent. Do not compress the image into a small shape vocabulary or require a legacy terrain schema. Resolve enough terrain, road, and water-system structure for the first dependent asset batch, while retaining the ability to adjust local decisions. Update the same expanded prompt with spatial decisions and run its full completeness check. A second asset-layout image is optional for complex worlds.
4. **Build the integrated terrain, roads, water, assets, and presentation.** Read [the world contract](references/world-contract.md). For outdoor terrain, let the agent directly generate or modify the actual Three.js project from the semantic image and scene requirements. Terrain, roads, and the water system are one spatial system: road alignments and grading as well as river, tributary, lake, riverbed, bank, and shoreline relationships may shape local terrain and must be resolved before dependent assets are placed. Use any currently available Meshy or Hyper3D provider according to the world contract; generated subjects must supply their planned visible forms. If at least one provider is available, the unified generated-subject quantity, category, regional coverage, and visual acceptance requirements still apply. Generate independent assets in dependency-aware batches, wait and download them independently, and integrate a ready batch together rather than editing the scene after every model. Buildings default to direct contact with finalized terrain or another real bearing surface; add foundations or platforms only when the design and terrain justify them, never a generic slab under every building. Check each region against the design and record implementation locations, initialization entry points, seeds, and asset paths. Design every major visible surface, including open and distant areas. Measure before reducing detail; record blockers in `.world/validation-report.md`.
5. **Perform semantic environmental fill.** After terrain, roads, visible water, major generated subjects, and key buildings are complete, run the scene and inspect panorama, overhead, midrange, route, and low-angle views. Follow the [fill rules](references/world-contract.md#semantic-environmental-fill): identify each region's surface type, use, and missing information; add suitable environmental assets while preserving passage and sightlines. Environment fill assets do not replace the unified major-generated-subject requirement. Give repeated environmental assets visible variation in model or prototype, scale, pose, rotation, material, color, maturity, wear, grouping, or density; instancing may share geometry for performance but must not produce a copy-paste appearance. For water, select scene-appropriate combinations of wind ripples, soft reflections, shoreline/depth color changes, rain response, fish, ducks, drifting boats, and click ripples. Keep road space clear while filling. Use stable seeds or explicit parameters, instancing, and quantity budgets. Record regions, asset types, providers, distribution rules, paths, performance, and before/after findings in `.world/validation-report.md`; recheck panorama, routes, low angles and local contacts before final validation.
6. **Inspect, repair, and recheck.** Read [the validation guide](references/validation.md). Check build, loading, and input, then use `game_use` in this order: whole world, regions and routes, major subjects, local details, then the whole world and presentation again, including narrow viewports. Check landform, road, and water-system relationships against the agent record and semantic image, continuity of visible information, applicable provider requirements and generated-subject count/categories/coverage, building orientation relative to roads, rivers, terrain, and public spaces, semantic information across all major visible and open areas, water behavior and color/depth response, environmental variation rather than copy-paste repetition, road continuity and building/asset clearance, and actual building contacts without unexplained repeated generic bases. Repair overall problems before extensive local refinement, then recheck affected views and routes. Keep evidence, deviations, and unverified items in `.world/validation-report.md`; names, builds, and counts do not establish visual completion.
7. **Deliver for review.** Provide the runnable world entry, necessary controls, and useful source locations. Keep detailed checks, generation and repair history, evidence, and limitations in `.world/validation-report.md` rather than repeating them in the final reply. A concise handoff does not make unmet requirements complete; if the world cannot build or open, state that no usable result is available. Leave final visual approval to the user.

## Revisions

Read the existing design, relevant code, and feedback first. Change only affected subjects and necessary connections, preserving unrelated regions and functions. Update the design and validation records, including changed requirements and reasons, and recheck appearance, routes, and interactions. A local revision does not require rerunning terrain-image generation, rebuilding the world, or generating 15 new models. When the request involves model replacement, follow the [world contract](references/world-contract.md): load and inspect the new model before removing the old one, handle unused resources, and retain comparable before/after views under the [validation guide](references/validation.md).

## OhMyGame Contract

- Follow the workspace's `AGENTS.md`. In an existing project, preserve its build tool and output layout unless the user requests a migration.
- OhMyGame runs the preview. Do not leave a development server or other background process running after the turn, and do not ask the user to open a local URL. Run a build when you need to check compilation.
- Keep the world responsive inside an iframe without horizontal overflow.
- When publishing is in scope, produce static output supported by OhMyGame.
- Do not install Playwright, Puppeteer, browser binaries, or global dependencies. Keep caches, logs, and screenshots out of the shipped project.
- Never claim visual or interaction checks that were not actually performed.
- Use Three.js and only generation capabilities actually exposed by OhMyGame, with Meshy or Hyper3D selected from current availability, configured credentials, quota, and scene needs. Do not require a fixed generator tool name or search for an unavailable provider. Never introduce Blender, `bpy`, or `.blend` intermediates. Never read, store, or pass API keys, create credential `.env` files, or bypass the platform with provider HTTP scripts.
